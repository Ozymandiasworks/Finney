## G1 — Windows/provider/backend proposal

The locked source has LevelDOWN6.1.0;6.1.1 below is an unselected proposal requiring separately authorized dependency alignment and exact native evidence. Initial acceptance proposal: packaged Windows x64, Electron44.3.0 locked by reviewed source; main-owned native `level7.0.1/leveldown6.1.1` authority store; Electron safeStorage Windows current-user DPAPI anchors; standard Node crypto from that exact packaged Electron runtime. Build tools Node24.19.0/Yarn1.22.22 are separate from embedded Electron Node/OpenSSL. Package identity/signature, Windows build/filesystem/device, loaded native ABI and binary hashes must be fixed in later acceptance evidence; no package has been accepted by this design. Browser/mobile/Linux/macOS and missing/unknown protection providers are UNSUPPORTED, with no plaintext fallback.

Proposed mapped locations under main-resolved userData: `wallet-authority-v1/<profile-id>/` for P, `wallet-lifecycle-v1/` for L; main validates canonical volume/file IDs, parent ownership/ACL and absence of reparse-point escape. Logical names are not renderer paths. Anchor/profile mapping is fixed by installed package identity and installation record; alternate userData/origin/partition requires explicit isolated import, never silently discover-and-rewrite. Legacy adapter must pin observed package/origin/partition/namespaces/schema mapping before any migration; unknown tuple is unsupported and leaves all source bytes. New origin proposal `app://finney/index.html`, trusted UI `app://finney/trusted.html`, packaged-only registered standard secure scheme, fixed resource loader denying remote/path traversal, distinct trusted WebContents. Exact scheme registration/Origin behavior requires packaged test. Different mapping requires a revised selected policy, not permissive prefix match.

Ordinary/trusted windows: nodeIntegration=false, contextIsolation=true, sandbox=true, webSecurity=true; no remote/native/general filesystem/raw IPC bridges. Block navigation/popups and direct shell calls. No `--no-sandbox` acceptance launch. CSP packaged-only scripts/styles with narrowly justified local assets, no remote script, eval or unsafe dynamic execution; trusted window no message HTML. Capability tests inspect actual package/preload, not source flags alone. Signal remains disabled.

DPAPI protects account-bound anchors; it does not isolate a compromised same-user host, provide portable recovery, authenticate an unprotected expected database root or guarantee erasure. Missing backend/provider error is not an empty wallet. Standard AEAD and authenticated graph F1 provide record/context checks; fully copied valid state lacks independent freshness. No TPM/remote freshness service is introduced. [Electron safeStorage source documentation](https://raw.githubusercontent.com/electron/electron/v44.3.0/docs/api/safe-storage.md).

Durability proposal D-sync: native WriteBatch atomicity within **one** DB plus `sync:true` acknowledgement, actual native backend lock and flush mapping verified. Application awaits callbacks/promises; timeout after submission is unknown. Source/content/installation separate stores use explicit journals, not a pretend cross-store transaction. Filesystem backup requires same-volume temp-write, awaited FlushFileBuffers-equivalent for file and supported durable publication/directory-entry procedure. If Node/Electron APIs cannot prove selected Windows publication barrier, qualification/last-source retirement stay blocked; no read-back substitute. A future separately reviewed storage adapter may supply missing primitive. [Pinned LevelDOWN contract](https://raw.githubusercontent.com/Level/leveldown/v6.1.1/README.md).

Evidence tiers: mock sequencing proves reducer logic only; native backend delayed/error/callback tests prove configured API behavior; controlled process termination/reopen proves only tested process-crash behavior; OS crash/power-cut/filesystem fault campaign must separately test the claimed durable-write model, write cache/device behavior and deletion publication. D-sync claims synchronous requests and bounded process-recovery under tested assumptions, **not unconditional physical power-loss survival**. Owner stronger D-power choice additionally blocks cutover/effects/retirement until dedicated storage-crash evidence. Even D-sync requires backend error/flush mapping and recovery source qualification; statements about test coverage identify exact failure model.

## G2 — Old-client and profile policy alternatives

M-A isolated acquisition from immutable offline source, then distinct new profile (D1). Retain/disclose originals and prevent supported updater/launcher from opening acquired old profile for active use. M-B same-profile acquisition is explicitly UNSUPPORTED_WORKFLOW in this version; its alternative can only be selected as defer-until-reviewed, not as an enabled path. M-A is fully specified in D1 and still requires source exclusion after every restart. Old executables cannot be constrained by a version check implemented only in new code. Supported installer/launcher denial plus locked/quarantined legacy source is required; external copied binaries/stores remain a residual risk, not proven prevention. Cooperative coexistence is not a viable cleanup/authority policy. Owner may defer migration until isolation available; no weaker automatic path.

Unknown schemas are never opened in create/repair mode. Explicit converter/import supports only enumerated legacy versions with exact map/evidence; unrecognized schemas are preserved, not downgraded. No source cleanup while an old writer, mapping ambiguity, unsupported backend or unaccounted residual exists in selected scope. Residual copies and valid-store rollback disclosures remain separate owner choices, not erased by new protected storage.

## G4 — External-browser consent and privacy contract

External launch is a distinct effect outside wallet/transport network policy. Owner alternatives X-off disables all shell launching (return POLICY_PENDING/UNSUPPORTED); X-consent permits **one destination-bound launch per trusted ceremony**. No automatic nav forwarding; `will-navigate`, popup and window-open events are denied and may display a passive main-validated link choice, never call shell. Ordinary click/userActivation/renderer boolean alone is insufficient.

Main constructs a destination handle A3 from known content/configuration. Normalization uses pinned WHATWG URL parser: require absolute http/https; reject credentials, NUL/C0/DEL/unpaired surrogates, backslashes and malformed percent escapes; validate serialized URL length<=2048, hostname IDNA ASCII shown alongside original Unicode label; preserve exact encoded path/query/fragment semantics without decode-and-reencode substitution, normalize only parser-defined scheme/host/default-port rules. IP literals permitted only as visibly displayed exact destination under owner-approved X-consent; no auto resolution or preload. Display complete canonical serialized href, scheme/host/port/path/query/fragment and privacy warning in trusted surface; no hidden/truncated destination may be approved. Reparse canonical href and require exact serialization equality before dispatch.

Grant binds canonical href digest, source message/config handle, requesting caller document/epoch, installation/profile lifecycle, one-use nonce and <=120s monotonic expiry. Trusted acceptance triggers main exact `shell.openExternal` once after grant consumption recorded; if crash/unknown result, no automatic retry on restart. Cancellation/reload/navigation/handle mutation invalidates; repeat requires fresh consent. Shell receives **only** validated href with no argument/options supplied by renderer. No clipboard/network request is an alternate fallback. Launch outcomes exposed as submitted/unknown/failed, not evidence browser connected.

Exact consent wording proposal: “Open this address in your system browser? That browser uses its own network and privacy settings and may connect outside Finney’s Tor route. The destination can observe information sent by that browser.” This is a boundary disclosure, not a claim a bypass has been measured. X-consent includes this warning each time; no remember/always-allow in this version. Historical nonsecret launch/task records can enter the complete backup, but no executable grant enters it or survives restore. B7 External plus A7 Task supply persistent dispatch-intent/consume identity. HTTP transport confidentiality warning shown for http links. Destination attacks/encoding changes must either canonicalize to displayed identical href or require new approval.

## G7 — Remaining adoption blockers and evidence separation

All technical definitions and alternatives offered for this bounded proposal are in the eight neutral documents. Explicitly unavailable alternatives are M-B same-profile acquisition, local removal of retired-generation keys, terminal protected-content compaction and retained-generation reactivation; choosing to require any needs a complete further reviewed contract. Their typed refusals preserve current recovery and confer no implementation approval. Portable graph recovery, current-content-retention disclosure and the first valid R-keep retirement are still required positive paths, not deferred to make the proposal easier. R96 is a proposed supported limit; imported authentic larger state remains preserved and unavailable rather than filtered. Owner selection of a supported option is pending in every case.

Not established by this documentation: trusted T2 provider with all required binding, native Windows durable directory/publication primitive, maximum actual backend amplification, packaged memory/latency/nonce ledger performance, actual independent full-graph serialization and coverage vectors, complete maximum offline restore, actual AES service/lifecycle implementation and storage-crash behavior. These are implementation/adoption prerequisites; no untested pseudocode is substituted for their evidence. No alternate crypto primitive, default policy or fallback follows from failure. OS/provider support outside the initial Windows proposal remains unavailable. Any missing definition identified during re-review blocks the dependent implementation until versioned and adjudicated.

All planned D/W/R/REG fixtures remain UNEXECUTED. Mock reducers, independent primitive/encoder experiments, native process interruption, actual packaged integration and storage-crash/power-loss campaigns must have separate results. A reopen test alone cannot establish power-loss durability. External human cryptography integration remains required before format/key-hierarchy adoption, sensitive reliance or recovery-dependent retirement.
